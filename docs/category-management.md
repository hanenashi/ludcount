# Category Management Decision

Phase 5 does not add category persistence. Ludcount currently ships a fixed,
localized category catalog in `src/features/transactions/model.ts`.

## Current behavior

- Built-in IDs are stable, language-independent keys such as
  `expense.groceries` and `income.salary`.
- Czech and English labels come from the translation dictionaries.
- Every transaction stores the category ID and a label snapshot.
- The form and filters use the built-in catalog only.
- Unknown historical IDs remain readable through their stored label snapshot.
- There is no categories collection, custom-category UI, archiving, renaming, or
  ordering preference.

This is intentional. Adding a speculative collection during polish would create
an untested data and authorization contract.

## Required schema work

Full custom and archived category support should add:

```text
households/{householdId}/categories/{categoryId}
  kind: "system" | "custom"
  systemKey: string | null
  customName: string | null
  transactionType: "income" | "expense"
  sortOrder: integer
  archived: boolean
  createdBy: userId
  createdAt: timestamp
  updatedAt: timestamp
```

Before implementation, decide whether built-ins are materialized as documents
or whether documents act as overrides for the code-defined catalog. Overrides
avoid seeding every household, but the repository must merge built-ins and
overrides deterministically.

The implementation would also require:

- a typed category converter and household-scoped repository
- stable custom IDs generated by Firestore
- an exact-field runtime validator
- a compound index for `transactionType`, `archived`, and `sortOrder` if the
  repository queries those fields together
- a settings route for create, rename, reorder, and archive operations
- forms that exclude archived categories from new transactions while still
  rendering historical transactions
- a documented policy for whether history shows the live category name or the
  transaction's label snapshot
- emulator-safe migration or lazy initialization for any built-in overrides;
  no manual collection creation

## Required security-rule work

The production rules would need a new
`households/{householdId}/categories/{categoryId}` match block that:

- denies unauthenticated and non-member reads
- permits category management only to the chosen household role; owner-only
  writes are the conservative default
- rejects arbitrary fields
- validates `kind`, transaction type, integer sort order, archive state, string
  lengths, and timestamps
- requires `systemKey` only for system entries and `customName` only for custom
  entries
- makes kind, system key, creator, and creation timestamp immutable
- prevents physical deletion once a category may be referenced; archive
  instead

Transaction rules would also need to validate that:

- built-in IDs belong to the submitted transaction type
- a custom category exists in the same household
- its transaction type matches the transaction
- it is not archived when creating a new transaction
- existing transactions may retain an archived category during unrelated edits

Those checks require matching Firebase Rules Unit Testing allow/deny cases for
member reads, owner writes, non-owner writes, malformed documents, cross-type
use, archived-category creation, immutable fields, and referenced-category
deletion.

No part of this schema or rules design has been deployed or created in
production.
